# Инструкция `sym_dispatcher`: запуск клиентской миссии

## Назначение

Эта инструкция задает порядок работы диспетчера от входящего сигнала до управляемой передачи исполнения на слой 3.

Главный принцип: слой 2 не исполняет клиентскую работу руками вместо профильного агента. Слой 2 принимает сигнал, выбирает правила, клиента, тип миссии, роли, инструменты, собирает `Runtime Contract` и контролирует evidence/acceptance.

## Обязательные базы перед запуском

Диспетчер начинает не с ответа, а с чтения баз:

| Что выбрать | Где смотреть |
|---|---|
| Карта баз диспетчера | `D2_ARCH-SYM-DISP-00_КАРТА_БАЗ_ДИСПЕТЧЕРА` |
| Правила и источники истины | `D2_ARCH-SYM-DISP-RULE_INDEX` |
| Тип миссии | `D2_ARCH-SYM-DISP-MISSION_TYPE_REGISTRY` |
| Агенты и роли | `D2_ARCH-SYM-DISP-AGENT_LAYER_REGISTRY`, `D2_ARCH-SYM-DISP-РЕЕСТР_АГЕНТОВ` |
| Продукты и мастер-контуры | `D2_ARCH-SYM-DISP-PRODUCT_REGISTRY`, `<рабочая папка> |
| Источник входящего сигнала | `D2_ARCH-SYM-DISP-INTAKE_SOURCE_REGISTRY`, `D2_ARCH-SYM-DISP-РЕЕСТР_АДАПТЕРОВ` |
| Статус подключения источника | `D2_ARCH-SYM-DISP-CONNECTOR_STATUS_MATRIX`, `D0_RULE-SYM-DISP-SOURCE_CONNECTION_PROTOCOL` |
| Инструменты | `D2_ARCH-SYM-DISP-TOOL_REGISTRY`, `D2_ARCH-SYM-DISP-TOOL_STATUS_MATRIX`, `D0_RULE-SYM-DISP-TOOL_HEALTH_PROTOCOL` |
| Клиентский маршрут | `D2_ARCH-SYM-DISP-CLIENT_ROUTING_REGISTRY`, `D2_ARCH-SYM-DISP-РЕЕСТР_КЛИЕНТОВ`, `D0_RULE-SYM-DISP-CLIENT_ROUTING_PROTOCOL` |
| Физические зеркала | `D2_ARCH-SYM-DISP-PHYSICAL_MIRROR_REGISTRY` |
| Карточка миссии | `D4_WORKDOC-SYM-DISP-ШАБЛОН_MISSION_CONTROL_CARD` |
| Runtime Contract | `D4_WORKDOC-SYM-DISP-ШАБЛОН_RUNTIME_CONTRACT` |
| Журнал запуска | `D4_WORKDOC-SYM-DISP-ШАБЛОН_DISPATCHER_RUN_LOG` |

## Термины исполнения

| Термин | Определение |
|---|---|
| Входящий сигнал | Сырой запрос, письмо, сообщение, файл или запись из источника до нормализации. |
| Источник | Канал появления сигнала: Codex chat, Telegram/бот, почта, Bitrix24, папка, Obsidian, webhook. |
| Адаптер | Механизм слоя 2, который превращает сырой вход в единый `Dispatch Event`. |
| Dispatch Event | Нормализованная запись о входе: кто написал, откуда, что просит, какие вложения, когда принято. |
| Signal Card | Физическая карточка входящего сигнала в клиентской или временной папке. |
| Client Route | Решение диспетчера, к какому `client_id`, проекту и папке относится сигнал. |
| Mission Type | Типовая миссия из реестра: например клиент_INVEST_FINANCE, CLIENT_ONBOARDING, DOC_CHECK. |
| Mission Control Card | Управленческая карточка миссии: цель, клиент, режим, роли, сроки, артефакты, acceptance. |
| Rule Pack | Набор правил слоя 1, которые обязательны для миссии. |
| Reference Pack | Собранный пакет источников истины, документов клиента и контекстов, которые можно давать исполнителю. |
| Product Pack | Обязательная часть Runtime Contract: реестр продуктов, связанные с миссией продукты и точные пути их мастер-контуров. |
| Agent Pack | Набор ролей и агентов слоя 2/3, допущенных к миссии. |
| Tool Pack | Набор инструментов со статусом допуска, нужных для миссии. |
| Runtime Contract | Передаточный контракт от диспетчера к исполнителю слоя 3: что делать, на каких данных, чем, куда положить результат. |
| Runtime Handoff | Факт передачи `Runtime Contract` конкретному исполнительному агенту. |
| Evidence | Проверяемый след исполнения: файл, лог, карточка, ссылка, выгрузка, результат теста. |
| Acceptance | Приемка результата по критериям миссии и правилам безопасности. |

## Обязательная продуктовая проверка

До выбора исполнителя Диспетчер читает `<рабочая папка> и определяет, относится ли миссия к существующему продукту. Каждый субагент получает Product Pack независимо от своей специализации. Новый продукт создается только в `<рабочая папка> при отсутствии записи открывается `PRODUCT_REGISTRATION_GATE`.

## Режимы работы диспетчера

| Режим | Когда применяется | Что делает диспетчер |
|---|---|---|
| `intake_only` | Нужно только принять и зафиксировать сигнал. | Создает `Dispatch Event` и `Signal Card`, не запускает миссию. |
| `routing_gate` | Неясен клиент, проект, тип миссии или источник. | Открывает gate, собирает недостающие признаки, не передает слой 3. |
| `mission_preparation` | Клиент и миссия понятны, но нужно собрать пакет. | Формирует MCC, Rule Pack, Reference Pack, Agent Pack, Tool Pack. |
| `runtime_handoff` | Все gates закрыты, можно запускать исполнителя. | Выпускает `Runtime Contract` и передает агенту слоя 3. |
| `acceptance_followup` | Исполнение завершено, нужен контроль. | Проверяет evidence, acceptance, обновляет реестры и клиентскую историю. |

## Алгоритм запуска

### 0. Загрузка ядра

Диспетчер открывает `D2_ARCH-SYM-DISP-00_КАРТА_БАЗ_ДИСПЕТЧЕРА` и `AGENT_MANIFEST.json`.

Результат шага: подтверждено, что инструкция, базы и рабочие папки доступны.

### 1. Нормализация входа

Сырой сигнал проходит цепочку:

```text
incoming_signal -> source_id -> adapter_id -> Dispatch Event -> Signal Card
```

Диспетчер определяет источник по `D2_ARCH-SYM-DISP-INTAKE_SOURCE_REGISTRY` и адаптер по `D2_ARCH-SYM-DISP-РЕЕСТР_АДАПТЕРОВ`.

### 2. Gate источника

Если источник имеет статус `connected` или `manual_active`, диспетчер продолжает.

Если источник имеет статус `planned`, `needs_credentials`, `to_check`, `blocked`, открывается `SOURCE_CONNECTION_GATE`.

### 3. Gate инструмента

Диспетчер проверяет, какие инструменты нужны для обработки сигнала и будущей миссии, по `D2_ARCH-SYM-DISP-TOOL_REGISTRY`.

Инструмент допускается в `Runtime Contract`, только если его статус в `D2_ARCH-SYM-DISP-TOOL_STATUS_MATRIX` позволяет выполнение или владелец продукта явно разрешил запуск в G-режиме.

### 4. Клиентская маршрутизация

Диспетчер определяет `client_id` по `D2_ARCH-SYM-DISP-CLIENT_ROUTING_REGISTRY`:

```text
Dispatch Event -> признаки клиента -> client_id/project_id -> client folder -> Signal Card path
```

Если клиент неизвестен, диспетчер не угадывает. Он открывает `CLIENT_IDENTIFICATION_GATE` или `CклиентTE_NEW_CLIENT_GATE`.

### 5. Выбор типа миссии

Диспетчер выбирает `mission_type` по `D2_ARCH-SYM-DISP-MISSION_TYPE_REGISTRY`.

Если подходят несколько типов, выбирается главный тип миссии и фиксируются вспомогательные. Если главный тип не выбран, открывается `MISSION_TYPE_GATE`.

### 6. Сбор Rule Pack

Диспетчер выбирает обязательные правила по `D2_ARCH-SYM-DISP-RULE_INDEX`.

Правила слоя 1 входят в миссию не как справка, а как ограничения для слоя 3.

### 7. Сбор Agent Pack

Диспетчер выбирает:

- владельца миссии слоя 2;
- исполнителя слоя 3;
- валидатора или приемщика;
- дополнительные роли, если миссия требует экспертизы.

Источник выбора: `D2_ARCH-SYM-DISP-AGENT_LAYER_REGISTRY` и `D2_ARCH-SYM-DISP-РЕЕСТР_АГЕНТОВ`.

### 8. Сбор Tool Pack

Диспетчер формирует перечень инструментов, которые исполнитель может использовать, и фиксирует ограничения.

Запрещено передавать исполнителю инструмент без понятного статуса, если результат может затронуть деньги, право, публичное обещание, клиентские данные или необратимое перемещение файлов.

### 9. Создание Mission Control Card

Диспетчер создает или обновляет MCC по `D4_WORKDOC-SYM-DISP-ШАБЛОН_MISSION_CONTROL_CARD`.

Минимум в MCC:

```text
mcc_id:
client_id:
project_id:
mission_type:
owner_layer_2:
executor_layer_3:
mode: R/G/БРОСОК
goal:
inputs:
outputs:
acceptance_criteria:
evidence_path:
status:
```

### 10. Сбор Reference Pack

Reference Pack содержит только разрешенные источники:

- правила слоя 1;
- документы клиента;
- историю релевантных миссий;
- карточку входящего сигнала;
- ограничения по безопасности;
- ссылки на физические папки и Obsidian-узлы.

### 11. Выпуск Runtime Contract

Диспетчер заполняет `D4_WORKDOC-SYM-DISP-ШАБЛОН_RUNTIME_CONTRACT`.

Runtime Contract должен быть достаточен, чтобы исполнитель слоя 3 мог начать работу без догадок.

### 12. Передача на слой 3

Диспетчер передает `Runtime Contract` выбранному исполнителю.

Слой 3 исполняет только в пределах контракта. Если исполнителю нужны новые данные, инструменты или изменение цели, он возвращает запрос диспетчеру, а не расширяет задачу сам.

### 13. Сбор evidence

Исполнитель возвращает результат и evidence в путь, указанный в контракте.

Диспетчер проверяет, что evidence существует, открывается и соответствует acceptance criteria.

### 14. Acceptance

Если результат принят, диспетчер обновляет MCC, клиентскую историю и нужные реестры.

Если результат не принят, диспетчер фиксирует причину, возвращает миссию на доработку или открывает gate.

### 15. Обновление операционного следа

Диспетчер обновляет:

- MCC;
- `Signal Card`;
- `Dispatcher Run Log`;
- клиентскую папку;
- реестр клиентов при необходимости;
- реестр инструментов/агентов/миссий, если выявлен новый факт;
- дневной протокол, если изменение архитектурное.

## Stop-gates

| Gate | Когда срабатывает | Действие |
|---|---|---|
| `SOURCE_CONNECTION_GATE` | Источник не подключен или не имеет evidence подключения. | Не запускать слой 3; создать тест источника. |
| `TOOL_HEALTH_GATE` | Нужный инструмент не проверен или имеет красный статус. | Убрать инструмент из Tool Pack или запросить G-режим. |
| `CLIENT_IDENTIFICATION_GATE` | Клиент не определен. | Положить сигнал во временную папку и запросить признаки клиента. |
| `CклиентTE_NEW_CLIENT_GATE` | Клиент новый, но нет полного набора атрибутов. | Заполнить шаблон создания клиента. |
| `MISSION_TYPE_GATE` | Не выбран главный тип миссии. | Не создавать Runtime Contract; уточнить признаки миссии. |
| `RULE_PACK_GATE` | Нет обязательных правил или источников истины. | Остановить запуск до сборки Rule Pack. |
| `AGENT_ADMISSION_GATE` | Исполнитель не закреплен, не найден или не допущен. | Выбрать другого агента или открыть задачу на настройку. |
| `RUNTIME_CONTRACT_GATE` | Контракт неполный. | Доработать контракт до передачи слоя 3. |
| `EVIDENCE_PATH_GATE` | Нет места записи результата. | Создать папку evidence до запуска. |
| `ACCEPTANCE_GATE` | Нет критериев приемки. | Не запускать исполнение до описания acceptance. |

## Граница слоя 2 и слоя 3

| Вопрос | Слой 2: диспетчер | Слой 3: исполнитель |
|---|---|---|
| Кто клиент? | Определяет и маршрутизирует. | Использует как вход. |
| Какая миссия? | Выбирает тип и режим. | Исполняет выбранный тип. |
| Какие правила? | Собирает Rule Pack. | Соблюдает Rule Pack. |
| Какие документы можно читать? | Собирает Reference Pack. | Читает только переданный пакет. |
| Какие инструменты можно использовать? | Формирует Tool Pack и gates. | Использует только разрешенные инструменты. |
| Где результат? | Задает output/evidence paths. | Кладет результат туда. |
| Кто принимает? | Назначает acceptance. | Передает evidence на приемку. |

## Минимальный выход диспетчера

Перед запуском слоя 3 диспетчер обязан выдать:

```text
run_id:
signal_id:
source_id:
adapter_id:
client_id:
project_id:
mission_type:
mode:
MCC:
Rule Pack:
Reference Pack:
Agent Pack:
Tool Pack:
Runtime Contract:
executor_agent:
validator_agent:
evidence_path:
next_gate:
```

## Критерии готовности инструкции

Инструкция считается применимой, если:

- каждый запуск миссии оставляет `Dispatcher Run Log`;
- каждая миссия имеет MCC;
- каждый исполнитель слоя 3 получает `Runtime Contract`;
- каждый `Runtime Contract` связан с Rule Pack, Reference Pack, Agent Pack и Tool Pack;
- неизвестный клиент, источник, инструмент или миссия останавливают запуск через gate, а не уходят в догадку.
