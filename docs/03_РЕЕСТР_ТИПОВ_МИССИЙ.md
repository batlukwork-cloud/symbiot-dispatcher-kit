# MISSION_TYPE_REGISTRY

Назначение: помочь диспетчеру определить тип миссии по признакам входящего сигнала и сразу выбрать роли, инструменты, граф и gates.

## Статус проверки

Проверено 2026-08-09.

Вердикт: `YELLOW -> WORKING`. Изначально реестр содержал базовую таблицу типов миссий, но не давал диспетчеру достаточного алгоритма выбора. Добавлены: определение `mission_type`, дерево решений, расширенная матрица маршрутизации, паспорта ключевых типов миссий, обязательные выходные артефакты и стоп-условия перед запуском слоя 3.

## Определение

`mission_type` - это типовой маршрут работы диспетчера, который отвечает на четыре вопроса:

1. что пришло на вход;
2. какой клиент или контур затронут;
3. какие правила, роли, агенты, источники и инструменты надо включить;
4. какой результат и evidence должны появиться до закрытия миссии.

`mission_type` не равен задаче. Одна задача может породить одну главную миссию и несколько вторичных тегов, но в `Mission Control Card` всегда должен быть один главный тип.

## Дерево выбора миссии

Диспетчер выбирает тип миссии в таком порядке:

1. Если вход не разобран, сначала создать карточку входящего по `D4_WORKDOC-SYM-DISP-ШАБЛОН_КАРТОЧКИ_ВХОДЯЩЕГО_СИГНАЛА`.
2. Если клиент не определен, выбрать `CклиентTE_NEW_CLIENT` или оставить сигнал в `CLIENT-UNKNOWN` по `D2_ARCH-SYM-DISP-CLIENT_ROUTING_REGISTRY`.
3. Если клиент определен, проверить активные миссии клиента в `D2_ARCH-SYM-DISP-РЕЕСТР_МИССИЙ`.
4. Если запрос касается правил, папок, canvas, связей, ролей или архитектуры, выбрать системный тип: `ARCHITECTURE_AUDIT`, `ROLE_AGENT_SYNC`, `SOURCE_INGEST` или `TOOL_CONNECTION_CHECK`.
5. Если запрос касается содержательной клиентской работы, выбрать клиентский тип по признакам клиента и домена.
6. Если подходит несколько типов, главный тип выбирается по главному обещанному результату, а остальные пишутся как `secondary_tags`.
7. Если главный тип выбрать нельзя, MCC создается в статусе `routing_blocked`, слой 3 не запускается.

## Паспорта ключевых типов миссий

### TASK_INTAKE_ROUTING

Используется, когда владелец продукта ставит управленческую или рабочую задачу, но еще не ясно, кто должен ее исполнять.

Обязательные поля в MCC:

- исходный запрос;
- `client_id` или `CLIENT-SYM-CORE`;
- главный результат;
- `mission_type`;
- выбранный режим `R/G/БРОСОК`;
- исполнитель или причина `routing_blocked`.

Нельзя запускать слой 3, если задача не получила код, владельца слоя 2 и адрес результата.

### CLIENT_REQUEST_INTAKE

Используется, когда вход пришел как клиентский сигнал: файл, письмо, голос, ссылка, папка, сообщение или команда.

Диспетчер обязан:

- определить источник по `D2_ARCH-SYM-DISP-INTAKE_SOURCE_REGISTRY`;
- создать или обновить карточку входящего;
- определить клиента по `D2_ARCH-SYM-DISP-CLIENT_ROUTING_REGISTRY`;
- нормализовать запрос;
- решить: создать новую MCC или присоединить сигнал к существующей миссии.

### CклиентTE_NEW_CLIENT

Используется, когда сигнал клиентский, но клиента нет в реестре.

Диспетчер обязан создать минимум:

- строку в `D2_ARCH-SYM-DISP-РЕЕСТР_КЛИЕНТОВ`;
- корневую папку клиента;
- папку `01_INBOX`;
- первую MCC;
- связь клиента с источником входа и активной миссией.

Без этих пяти элементов клиент считается не заведенным.

### CLIENT_INVEST_FINANCIER

Пилотный клиентский тип для клиент.

Физический исполнительский агент:

`<рабочая папка> AGENT\клиент_AI_AGENT_Инвестиционный_финансист`

Признаки выбора:

- в запросе есть клиент, девелопмент, ИДП, земля, объект, инвестор, финмодель, ТЭП, доходность, маржа, CAPEX, OPEX, cash flow, проектное финансирование, банк, эскроу, LOI или структура сделки;
- результат нужен как финансовый расчет, инвестиционный вывод, сценарий сделки, банковская упаковка или проверка экономики проекта.

Reference Pack должен включать:

- правила из `D2_ARCH-SYM-DISP-RULE_INDEX`;
- клиентский контур клиент из `D2_ARCH-SYM-DISP-CLIENT_ROUTING_REGISTRY`;
- агентский пакет `AGENT-клиент-INVFIN` из `D2_ARCH-SYM-DISP-AGENT_LAYER_REGISTRY`;
- методики: `D0_RULE-SYM-CORE-МЕТОДИКА_Финансовая_проверка_таблиц_и_расчетов`, `D0_RULE-SYM-CORE-МЕТОДИКА_Банковская_упаковка_и_проектное_финансирование`, `D0_RULE-SYM-CORE-МЕТОДИКА_Best_Use_Коммерческого_директора`;
- исходные клиентские документы и статус источников.

Стоп перед исполнением: нет исходных чисел, не указан проект/объект, не выбран формат результата или TOOL-EXCEL-SHEETS не проверен.

### ARCHITECTURE_AUDIT

Используется для проверки папок, canvas, Obsidian-ссылок, физического зеркала, правил и архитектуры.

Результат не должен быть только текстовым мнением. Нужны проверяемые факты:

- какие файлы/папки проверены;
- какие ссылки разрешаются;
- какие ссылки пустые или битые;
- что перенесено, оставлено, объединено или требует решения владелец продукта;
- где зафиксирован протокол.

### ROLE_AGENT_SYNC

Используется для ролей, паспортов, Word-зеркал, физических папок агентов и реестра агентов.

Минимальный результат:

- найденный физический корень;
- список ролей/агентов;
- статус зеркала Obsidian/физика/Word;
- дубли;
- решение по каждому спорному элементу: keep, merge, move, archive, delete_candidate.

### SOURCE_INGEST

Используется для новых документов, книг, методичек, файлов клиента, ссылок и материалов.

Диспетчер не должен сразу класть материал в постоянную библиотеку. Сначала:

- карточка входящего;
- статус источника;
- чувствительность/риск;
- клиент или контур;
- маршрут: библиотека, клиентская папка, методологический разбор, OCR, архив-кандидат.

### TOOL_CONNECTION_CHECK

Используется, когда надо проверить инструмент, плагин, адаптер, API, connector, CLI или runtime.

Инструмент можно передать в Runtime Contract только если статус в `D2_ARCH-SYM-DISP-TOOL_REGISTRY` `active` или есть отдельное `G`-решение на spike.

## Правило выбора миссии

Если вход подходит под несколько типов, диспетчер создает одну MCC с главным типом и вторичными тегами. Исполнение не запускается, пока не выбран главный `mission_type`.

## Стоп-условия

Диспетчер не передает миссию в слой 3, если:

- нет главного `mission_type`;
- нет `client_id` или явного решения работать в `CLIENT-UNKNOWN`;
- нет Rule Pack из `D2_ARCH-SYM-DISP-RULE_INDEX`;
- нет Agent Pack из `D2_ARCH-SYM-DISP-AGENT_LAYER_REGISTRY`;
- нет Tool Pack из `D2_ARCH-SYM-DISP-TOOL_REGISTRY`;
- источник входа не классифицирован по `D2_ARCH-SYM-DISP-INTAKE_SOURCE_REGISTRY`;
- для клиентской миссии не создана или не обновлена MCC по `D4_WORKDOC-SYM-DISP-ШАБЛОН_MISSION_CONTROL_CARD`;
- результат не имеет адреса хранения и acceptance gate.

## Acceptance для этого реестра

- [x] У каждого типа миссии есть признаки входа.
- [x] У каждого типа миссии есть слой 2, слой 3, инструменты и gates.
- [x] Есть алгоритм выбора при конфликте типов.
- [x] Есть связь с правилами, агентами, клиентами, источниками и инструментами.
- [x] Пилот клиент привязан к физическому агенту инвестиционного финансиста.
- [ ] Следующий проход: вынести каждый зрелый `mission_type` в отдельную карточку-паспорт, если количество типов превысит 12.
